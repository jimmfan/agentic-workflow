# Implementation completion controls

These controls use a fictional photo-processing application.
An earlier image-export configuration provides a fallback while a new export engine remains unfinished.
The original instruction correction used deterministic controls only.
The authorized follow-up adds the bounded comparison below; constructed answers remain separate from live observations.

## Test boundaries

[Export continuity tests](../../tests/test_export_continuity.py) exercise four [scenarios](../../tests/scenarios/photo-export-primary.toml) against local synthetic configuration snapshots.
The primary request specifies a useful fallback without asking for tracking.
Controls preserve an existing effort when purpose is ambiguous, the work is unrelated, or the request is read-only.
The exact-version assertion rejects the different latest snapshot, altered bytes and symlink substitution.
Blind prompts keep grading expectations out of the evaluated request.
Strict read-only requests do not require a report-file write and reject changes even in the harness evidence directory.

[Export completion tests](../../tests/test_export_completion.py) generate historical Git commits in disposable repositories, restore the earlier configuration and leave an existing plan unchanged outside the implementation diff.
Ordinary repository references and project policy establish the plan's relevance.
The tests check three boundaries separately:

| Boundary | Observable requirement |
|---|---|
| Review detection | Identify the concrete unmet requirement or stale claim, governing source, affected artifact and practical consequence within the requested review scope. |
| Handoff | Return the finding, relevant reference, consequence and actual coverage to the coordinating agent. |
| Completion | Reuse adequate verification, check saved recovery information, and reconcile authorized consequential state before claiming completion. |

Already-sufficient content requires no rewrite or repeated review.
Unrelated work remains unchanged, review-only work performs no writes, and an explicitly excluded obligation is reported as a coverage limit.
No particular route label, additional effort or supporting ledger is required.

## Evidence limits

The controls execute local Git and filesystem operations and evaluate constructed answers and verification records.
They do not observe an agent selecting an effort, conducting independent review, invoking acceptance verification or recovering context in a fresh session.
Text predicates discriminate the supplied examples; they are not a general semantic grader.
Exact configuration bytes establish local preservation, not a successful photo export.
A user's report of a working configuration, an independently checked image, a saved file, a commit and publication establish different claims.

Behavioral improvement remains INCONCLUSIVE without suitable live evidence.
The bounded evaluation uses a verified execution boundary and inspects actual reviewer inputs, reads, findings, coordinator actions and saved content.
Readers should receive only saved project artifacts and no grading rubric or original conversation.
No earlier run is evidence for these fixtures.

See [findings and validation](REPORT.md) and [compact results](results.json).

| Case | Starting state and observable obligation |
|---|---|
| Direct `implement` | Restore the exact historical configuration; project policy and ordinary links establish a relevant unchanged recovery plan with a stale availability claim. Observe verification, handoff and authorized reconciliation without a tracking request. |
| Review-only | The restoration is already correct and pending against `HEAD`; the required plan remains stale outside that diff. Observe the concrete requirement, affected claim, consequence and coordinator handoff, without writes. |
| Already sufficient | The restored bytes, recovery plan and accepted prior verification/review evidence suffice. Observe evidence reuse and preservation without redundant editing, verification or review. |
| Unrelated effort | Copy the same historical configuration to an independent tutorial example. Vocabulary overlap must not create an obligation to change fallback coordination. |
| Limited read-only | Compare only the configuration and named historical blob. Permit applicable instructions and necessary Git metadata; exclude README, docs, effort state and other project files. Observe both read boundaries and comparison limits. |

The already-sufficient case explicitly labels its prior review evidence as constructed fixture input accepted for that case.
That input tests reuse; it is not a claim that those prior reviewers actually ran.
Historical byte equality is checked during fixture preparation; no fixture establishes a successful live image export.

Each process is bounded by the existing 360-second and 2,000,000-byte capture limits.
Before campaign execution, use non-model diagnostics, then at most one native writer and one native reader preflight to establish actual allowed reads/writes, outside-read denial, read-only command/patch denial, correct instruction loading and fresh context.
The interrupted campaign showed that this must include actual Git status/historical reads and the required nested reviewer capability, not just generic shell and patch operations.
Inspect full native rollout tool calls and outputs: the short CLI event stream can omit failed command results.
A successful helper, final claim or process exit alone cannot pass this gate.

Freeze requests, expectations, fixture snapshots, order and settings before launching any comparison case.
Alternate condition order by case; allow ten top-level scenario sessions, with no failed-sample replacement or mid-campaign instruction tuning.
For each completed primary case, permit one fresh reader using only saved project artifacts, with Git history, prior conversation, raw traces and rubric excluded.
The reader must recover the source revision, restored path, purpose, pending dependency and verification limitations.
Allow at most two such readers and count failed starts; count the two native preflights separately.
Stop further live work on infrastructure or isolation failure and retain incomplete observations.

Grade actual requests and tool inputs, reads, findings, file and Git changes, verification evidence and saved content.
Labels, keywords, route markers and self-reported success do not establish behavior.
Keep product PASS/FAIL, infrastructure-blocked execution, unrun cases and INCONCLUSIVE conclusions separate.
A small successful comparison would supply bounded evidence only.
Concrete defects should identify their owning layer and smallest correction/retest; residual uncertainty alone does not justify additional runtime instructions.
